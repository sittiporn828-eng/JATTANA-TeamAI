# บทเรียนจากการสร้างระบบร้านอาหาร/ค้าปลีกหลายสาขา (Restaurant & Retail ERP lessons learned)

เอกสารนี้สรุปแนวคิดทั่วไปจากปัญหาที่เกิดจริงในโปรเจกต์ระบบบริหารร้านอาหาร multi-branch
(React + TypeScript + Postgres/Supabase + serverless functions) โดยตัดชื่อตาราง ชื่อฟังก์ชัน
รหัสโปรเจกต์ และตัวเลขทางธุรกิจออกแล้ว ใช้เป็นเช็กลิสต์ตอนออกแบบหรือรีวิวระบบแนวเดียวกัน

Keywords: costing, pricing, migration, release checklist, Postgres, RLS, idempotency, AI scan, LLM gateway,
audit, backup, rollback, Thai text, restaurant, retail, POS

## 1. ต้นทุน กำไร ราคา (costing & margin)
- คิดต้นทุน VAT GP margin ที่ฟังก์ชันกลางที่เดียว ห้ามหน้าไหนคิดเอง
- เป้ากำไรมีค่าเดียวทั้งแอป ห้ามเกณฑ์ตายตัวหรือเป้าแยกต่อหน้า
- ราคา ต้นทุน กำไรที่วางคู่กันต้องฐานเดียวกัน (ต่อเสิร์ฟกับต่อเสิร์ฟ) ป้ายหน่วยต้องตรงกับที่คำนวณ
- หน่วยต้นทุน: เก็บเป็นหน่วยเล็กสุด (กรัม/มล.) ห้ามเปลี่ยนหน่วยของรายการที่ถูกใช้ในสูตรแล้ว ให้ฐานข้อมูลกั้นด้วย trigger
- ตัวเลขสรุปต้องนับจากทุกแถว ไม่ใช่จากรายการ top-N และยอดรวมต้องเท่าผลรวมของช่องที่แสดง
- backfill ต้นทุนห้ามแตะราคาขายที่แคชเชียร์เก็บไว้

## 2. การบันทึกข้อมูลจากหน้าจอ (save patterns)
- ห้ามเขียนฐานข้อมูลทุกครั้งที่กดแป้น ทุก mutation ต้อง await และเช็กผลก่อนขึ้นคำว่า "สำเร็จ"
- อ้างอิงข้อมูลด้วย id ไม่ใช่ชื่อ ลบของที่ถูกอ้างอยู่ต้องเช็กและบอกว่าใครใช้
- ปิดหน้าต่างแก้ไขต้องล้าง id ที่กำลังแก้ และทุกทางเข้า "สร้างใหม่" ต้องเริ่มจากฟอร์มว่าง
  (เคยสแกนรูปแล้วบันทึกทับของเดิมที่เปิดล่าสุด)
- บันทึกหลายส่วน (หัวเอกสาร + บรรทัด) ใช้ RPC เดียวใน transaction เดียว
- request id หนึ่งตัวต่อเอกสาร สร้างตอนเริ่มและเก็บข้ามการลองใหม่ ห้ามสร้างใหม่เมื่อ payload เปลี่ยน
  ฝั่ง server ปฏิเสธ payload ต่างจากเดิมเฉพาะเมื่อครั้งก่อน commit แล้ว
- error ภาษาอังกฤษจากเครือข่าย/RPC แปลเป็นไทยที่จุดเดียว

## 3. ข้อมูลเข้า (สแกน AI, นำเข้าไฟล์)
- ผ่านหน้าตรวจก่อนบันทึกเสมอ ห้ามบันทึกบรรทัดที่ราคา 0 เงียบๆ
- บรรทัดปริมาณ 0 ให้เจ้าของใส่ค่าหรือเลือกข้าม อย่าส่งทั้งชุดแล้วล้มทั้งชุด
- ห้ามตัดแถวเงียบตอนอ่านไฟล์ (ไลบรารีบางตัวอ่านแค่ 10,000 แถวถ้าไม่ตั้งค่า)
- หลักฐานที่อ้างว่า "AI อ่านได้" ต้องเก็บโดยฝั่งเซิร์ฟเวอร์ อย่ารับสรุปการแก้ไขจากหน้าเว็บ (ปลอมได้)
- บิลที่ยอดรวมรวม VAT: เทียบทั้งแบบรวมและไม่รวม VAT ก่อนฟ้องว่ายอดไม่ตรง

## 4. ฐานข้อมูลและความปลอดภัย (Postgres / RLS)
- ตารางใหม่ต้องเปิด RLS ล็อกเจ้าของแถวใน with_check, FK + CHECK + index, คอลัมน์สถานะ/เงินไม่ให้ client เขียน
- bucket เก็บไฟล์ private + โฟลเดอร์ตามเจ้าของ + จำกัดขนาด; ไฟล์หลักฐานตั้งชื่อด้วย SHA-256 ห้ามเขียนทับ
- ของที่ผู้ใช้สร้างได้ต้องนับโควต้าและแสดงตัวเลขในแอป
- ตรวจรหัส/PIN ต้องไม่เป็น oracle: ทุกความล้มเหลวตอบเหมือนกัน นับครั้งผิดทั้งฝั่งผู้ถูกเดาและผู้เดา
- การคืนเงินต้องคืนตามวิธีที่จ่ายจริง และจำกัดเพดานต่อวิธีจ่าย
- โหลดแบบแบ่งหน้าต้องมี order ที่ไม่ซ้ำและมาจากคอลัมน์ลำดับจริง ห้ามเรียงด้วย uuid สุ่ม
- กรองข้อความไทยต้องเก็บ Unicode mark (\p{M}) ไม่งั้นสระและวรรณยุกต์หาย
- guard ที่เทียบ body ฟังก์ชันด้วย md5 ต้องตัด CR ก่อน (Windows checkout เป็น CRLF)
- สคริปต์ซ้อม/ตรวจบน production ต้องตั้ง statement_timeout ต่ำกว่าเพดานของ API ไม่งั้น query ค้างและถือ lock
- rehearsal ที่ raise เองต้องใช้ SQLSTATE ของตัวเอง อย่าใช้ P0001 เพราะ exception handler จะกลืน

## 5. ขั้นตอนปล่อยขึ้นระบบจริง (release flow)
1. แตก branch จาก main
2. build + test
3. ให้ reviewer อิสระตรวจ แก้ แล้วตรวจซ้ำ
4. สำรองฐานข้อมูลก่อนลง migration
5. ซ้อม migration แล้วลง production ก่อน merge (migration ที่ commit แล้วไม่ใช่ migration ที่ลงแล้ว)
6. เปิด PR รอ CI เขียวจริงบน commit สุดท้าย (อย่า pipe ผลเช็กไปคำสั่งที่ปิดบัง exit code)
7. merge ผูกกับ commit ที่ตรวจแล้ว (`--match-head-commit`)
8. รอ deploy แล้วตรวจหน้าเว็บจริงแบบอ่านอย่างเดียว
9. จดบทเรียนเป็นกฎ + เทสต์ ทุกปัญหาที่เกิดจริง
- ห้ามแก้ migration ที่ลง production แล้ว ให้เขียนไฟล์ใหม่
- ห้าม push ตรงเข้า main, ห้าม commit secret, ห้ามลง production โดยเจ้าของไม่สั่ง
- migration จากหลาย PR ชนเลขเวอร์ชันกันได้ เช็ก main + PR ที่เปิดอยู่ + production ก่อนตั้งชื่อ

## 6. AI gateway (LLM)
- เรียกโมเดลผ่านโมดูลกลางที่เดียว (เลือก provider, retry, fallback, แปลง body ตามโมเดล) ให้เปลี่ยนโมเดลที่เดียว
- retry เฉพาะข้อผิดพลาดชั่วคราว (5xx, 429 แบบ "คนใช้เยอะ") ส่วน 429 โควตา/บิลล์, 402, 400 คือจบ ไม่ retry
- fallback โมเดลเฉพาะบน provider แบบเสียเงิน ห้ามส่งข้อมูลลูกค้าไป free tier ที่อาจนำไปเทรน
- เปลี่ยน provider แล้วนับ token ต่างกันได้หลายเท่า ตั้งเพดานงบเป็นเงินแทนเพดาน token และอัปเดตตารางราคาก่อนใช้โมเดลใหม่
  (โมเดลที่ไม่อยู่ในตารางราคาจะ log ค่าใช้จ่ายเป็น 0 และเพดานไม่ทำงาน)
- เปรียบเทียบโมเดลด้วยข้อมูลจริง + benchmark ของระบบ แต่จำไว้ว่า prompt และเกณฑ์ถูกจูนกับโมเดลเดิม โมเดลอื่นเสียเปรียบ
- เมื่อ AI ล่มพร้อมกันทุกฟังก์ชัน ให้ไล่สาเหตุฝั่งบิล/บัญชี (บัญชีชำระเงินถูกระงับ, เครดิตหมด) ก่อนสรุปว่า "โมเดลคนใช้เยอะ"

## 7. ปฏิบัติการ (ops)
- สำรองฐานข้อมูลก่อนทุกรอบปล่อยที่มี migration และเก็บคีย์สำรองอย่างปลอดภัย ห้ามสร้างคีย์ใหม่ทับ
- งานตั้งเวลา (cron) อยู่ที่เดียว อย่าให้มีทั้ง GitHub Actions และ Worker ทำงานเดียวกัน
- ตรวจ traffic แปลกด้วย analytics จริง: สแกนเนอร์ที่ยิง path ลับ (/.env ฯลฯ) ควรได้ SPA HTML 200 ไม่ใช่ไฟล์จริง
  ยืนยันด้วย curl ก่อนตกใจ และแยก 504 ของ Cloudflare early-hints ออกจาก 504 ที่ผู้ใช้เจอ
- ใน LINE WebView (Android) `navigator.onLine` อาจเป็น false ทั้งที่ออนไลน์ ต้องยืนยันด้วยการยิงตรวจจริง
- Windows: หยุด dev server ตามพอร์ต ห้ามฆ่า node.exe ทั้งหมด; ไฟล์ SQL บน Windows เป็น CRLF

## 8. วิธีทำงานร่วมกับเจ้าของระบบ
- ตอบเป็นภาษาไทย รายงานตามจริงว่าอะไรทดสอบแล้ว อะไรล้ม อะไรข้าม
- ทุกบั๊กที่แก้ = กฎสั้นๆ + เทสต์ + บันทึกรายละเอียดในสกิลที่ตรงเรื่อง
- หลาย session ใช้ repo/ฐานข้อมูลเดียวกันได้ ให้ stage เฉพาะ hunk ของตัวเอง ห้าม `git add .`
- อย่าใช้ไฟล์ใน /tmp ร่วมกันข้าม session (เคยทำให้ PR body ถูกสลับ) ใช้โฟลเดอร์ scratch ของ session
