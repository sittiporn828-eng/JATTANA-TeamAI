# PRD Acceptance Review (fail-closed)

Review an implemented phase/feature against the PRD's acceptance criteria. Assume guilt until a test/run proves otherwise. Do NOT trust earlier reviews or claimed gate results — re-verify everything yourself. Used for phase-by-phase PRD reviews (Phase N acceptance gates).

## Steps

1. **Read the acceptance criteria first.** Grep the PRD for the phase heading, copy the exact criteria wording. Map every criterion to concrete code + a test.
2. **Re-run all claimed gates independently.** format check, lint, typecheck, build, full test suite. Count tests and compare to the claim (e.g. "46 = 34 + 3 + 9"). A claimed pass is a hypothesis, not a fact.
3. **Read the implementation end-to-end** (service + routes + tests), not just tests. Tests pass ≠ acceptance met: tests can enshrine broken behavior (e.g. a test asserting a kicked player can instantly rejoin).
4. **Detect stub implementations** — code that looks like the feature but doesn't do the thing:
   - Auth = raw id passthrough ("bearer token" IS the player_id); route that mutates an account without any auth check → account takeover. Real auth = opaque session tokens minted at login.
   - Hardcoded fake data (status: `'online'` for everyone, no presence tracking).
   - "Allocation"/"matchmaking"/"server" endpoints returning static env-configured URLs + random UUIDs without talking to the real service.
   - Settings stored but never consumed downstream (decorative room settings, unused party `queued` flag).
   - Cross-service contract mismatch: feature spans two services (API → game server); both test suites mask the gap — the game-server test passes the server's OWN id (self-referential), the API test uses a mocked peer. Trace the value A produces into B's validation: e.g. the API mints match_id X, `/allocate` echoes X back, but the WS server only accepts its own startup match_id → the returned ticket is unredeemable (MATCH_NOT_FOUND on every intent). **Always require an executable seam probe with the real built services and assert both sides' authoritative IDs; never fallback to a player-derived ID when the allocator omits its ID.**
   - Async lifecycle race: validation before an `await` is not atomic. For result/remake/release flows, synchronously claim the live entity (`running → settling`) before awaiting downstream cleanup; rollback the claim on failure; reject a second claimant. Validate all actor/entity IDs before mutation and require exact participant-set equality, not subset/overlap checks.
   - Password fields: ignored, or worse, deny access when set (passworded room unjoinable by anyone — no route accepts the password).
   - **In-memory Maps as the only store when the repo has a DB package → "progress persists" only within one process lifetime. For social/account phases, verify the production constructor actually enables the durable store; a persistence test that injects a temporary snapshot path does not prove the live server persists.
   - **Guest recovery bound only to a client/device id → account takeover/impersonation.** `client_id` is a lookup hint, not proof of ownership. Require an opaque recovery/session credential on repeat guest recovery, persist that credential, and test that client id alone creates a new guest while client id + credential restores the account.
   - **Session lifecycle incomplete → bearer tokens live forever.** Check expiry, explicit revocation/logout, persisted session metadata, and that `authenticate` rejects expired/revoked tokens. A random token minted once is not a complete session system.
   - **Room secrets leak through domain responses.** Hash room passwords with a per-room salt and constant-time comparison, then explicitly redact the password/hash from every create/admin/room response. Test both correct/incorrect join and response non-disclosure.
   - Unsalted single-pass hash for passwords; no constant-time compare.
   - Integer validation NaN hole: `team < 1 || team > 4` is false for NaN → NaN persists. Number.isInteger / zod schema required at trust boundaries. Same for `Math.floor(Number(body.x))` amount coercion — `'abc'` → NaN poisons xp/level state; Number.isFinite required.
   - No start-once / idempotency guard (calling start twice mints a second match).
   - **Feature tested but dead in production.** A service method can be unit-tested yet never called outside tests: grep every caller of the key method (e.g. `tickQueue`) excluding `*.test.ts` — if only tests call it, the feature (range expansion, tick loop) doesn't exist over the wire. Unit tests passing ≠ wired into the server.
   - **Early-return paths that skip resource cleanup.** Guard-returns (`if (result.valid === false) return`) placed BEFORE state teardown (busy set, locks, queue membership) leak the resource forever. Check every return path cleans up — invalid-result paths often skip rating AND skip cleanup, permanently bricking the entity.
   - **Auth ≠ authorization.** 401-gating every route is necessary, not sufficient. Any authenticated user can still (a) mutate other users' data by naming arbitrary ids in the payload (winner_id/loser_id/leaver_id with no match-membership check → rating forgery), or (b) trigger global mutations (season-reset endpoint callable by any player → ladder wipe). Global-mutation endpoints need an admin/role gate; per-entity mutations need proof the actor owns/participates in the entity.
   - **Route boundary truncates the domain type.** The service/domain type carries the full feature shape but the HTTP adapter maps only some fields (e.g. PostMatchStats has 17 fields, POST /postmatch persists 6). Verify by round-tripping a FULL-shape payload through the route and diffing the response — silent drops mean the server can never receive/store part of the acceptance (real case: damage/healing/timeline/graphs stats unreachable).
   - **Admin/GM console views can drop data the API serves.** API-level tests pass while the console renders blanks — check the console's table field arrays against the ACTUAL response keys: mismatched names → every cell empty (real case: fields `['id','hostId','region','status']` vs API `{room_id, invite_code, host_id, members, match_id}`), and `Object.entries(payload)` over a nested object renders `'[object Object]'` (queue per-mode counts invisible, only `total` legible). Also verify the console stores the session token from login and sends it on every call (not the raw admin token), and whether Logout calls the server revocation endpoint or only clears local state (local-only is bounded harm: 30-min expiry + server route exists — severity 'info'). Console-phase acceptance = API AND console view demonstrable; API-met + console-broken = 'partial', minor blocker, one-line field fix.
   - **Security control is declarative-only.** A method returns a delay/hiding contract (ranked spectator join → `{delaySeconds: 90, sensitive: false}`) but no data path enforces it. Find EVERY other endpoint exposing the same data (replay GET returned live seed + full event stream with zero delay for any session) and check the control applies there. A value handed to the client is not enforcement.
- **Replay must have a real producer and a real reducer.** Admin-only capture/event/input routes plus a `resimulate()` method that returns stored arrays are not acceptance. Capture at the allocation/match-start seam, append terminal events from the authoritative result path, and make `resimulate()` invoke a deterministic reducer over the recorded seed and inputs. Verify the same seed+inputs produce the same canonical event/state output; a repeated read of the same Map is not a determinism test.
- **Post-match must be server-derived at the terminal seam.** A full-shape admin payload round-trip proves mapping only, not authoritative stats. Trace ranked/game-server completion into post-match storage and assert at least winner/final score/XP/rating fields come from the server result; treat admin ingestion as an operational correction path, not the source of truth.
   - **Per-user toggle stored service-global.** Streamer-mode flag as one boolean on a singleton service → any authenticated user can flip it for ALL users (privacy off for everyone). Per-viewer state needs a per-actor Map, not a service field.
   - **TS union cast at the trust boundary.** `body.kind as ReplayEventKind` with no runtime check — arbitrary strings recorded into the typed event stream (verified 200 for kind='not-a-kind'). Validate against the union (`.includes`) → 400; same family as the NaN hole.
   - **Unknown-resource 500 vs 404 consistency.** A service that `throw`s on unknown id with no route try/catch yields 500 with the message leaked, where sibling routes 404 cleanly. Check for a setErrorHandler and compare sibling-route behavior (replay GET/seek unknown → 500; postmatch GET unknown → 404).
   - **Failure paths must restore pre-op state.** If a match search dequeues players and allocation then fails, are they re-enqueued? State taken early (dequeue, reserve, mark-busy) must be returned on every later failure — silent drops on transient infra failure violate the queue.
   - **Completion path must release what the new flow acquired.** When a phase extends match formation (e.g. 2v2/FFA matching now marks 4 players busy) but the result/report flow keeps the old shape (single winner+loser busy.delete x2), every normal completion strands the extra participants forever. For each NEW mode, count acquire (busy/queue/reserve) == release (result/remake/teardown) over the new flow's own path — the old mode's balance is not evidence.
- **Exact-match lifecycle invariants are mandatory at every terminal route.** For result/remake/release endpoints, authenticate the actor against the exact live match, reject duplicate or partial client participant lists (or derive participants server-side), and validate that every supplied ID belongs to the same match. Release the authoritative downstream allocation first; only then mutate rating, busy, live-match, or room state. A release failure must return a retryable error and preserve the binding/state. Add route-level regressions for cross-match forgery, duplicate/partial participants, and downstream release failure before declaring acceptance. Real case: 4-player match → only 2 ever freed → teammates only escape via /remake which docks the 'leaver' −32 Elo.
- **Await-boundary race:** validation before `await release()` is not atomic. Claim the live match synchronously (`running -> settling`) before the await; reject a second concurrent result/remake; on downstream failure restore `settling -> running`. Validate `winner_id`/`loser_id` membership before any auto-create helper, or forged IDs can mint and mutate rank accounts.
5. **Distinguish scope.** PRD features that belong to adjacent phases (matchmaking/rank/queue-cooldown) are NOT blockers for this phase — list as deferred. Only the phase's own acceptance criteria gate the verdict.

### Phase 8 competitive-modes checklist (2v2/FFA/team/pick-ban)

For a modes phase, do not accept pure rule helpers or client-callable demos as production acceptance. Trace the live-match seam end-to-end:

- 2v2 team formation must require an authoritative `match_id`, exact four-player roster equality, and actor membership; reject arbitrary IDs, duplicates, subsets, and cross-match rosters. The route must consume the roster created by ranked matchmaking.
- FFA winner calculation must filter the active list itself against server-computed non-eliminated scores. Filtering only the score map while passing the original client `active` list lets an eliminated high-score civilization win.
- Team bans must cross the allocation boundary: validate caps/deduplication, include the resulting `power_bans` in the ranked allocation request, and assert the allocator receives them. A `/teams/ban` response that merely echoes a computed list is decorative.
- Pick/ban tier must come from server-side rank for the authenticated player/mode, never from a query parameter. Define an explicit fallback for placement/unranked players and test that client-supplied `tier=MASTER` cannot escalate configuration.
- Shared team score is only a real seam when the team roster is authoritative and a production consumer exists. If the actual objective/game-server protocol is intentionally deferred, state that scope explicitly instead of claiming authoritative simulation acceptance.
- Add route regressions for eliminated-winner injection, arbitrary team IDs, client tier escalation, and bans reaching allocation; then run focused modes tests plus full gates and fresh review.

### Serial hardening workflow

When the user asks to finish a backlog serially, execute one blocker at a time: implement the smallest real fix, add one regression check, run the narrow gate, then immediately continue to the next blocker. Keep a live blocker list and never mark a phase passed from green unit tests alone.

- **Consume async review results immediately.** When a delegated fresh review completes, treat its verdict as the next actionable state: fix any blocker it found, rerun the affected gates, and re-review only if the tree changed. Do not keep reporting that a review is pending after its completion message has arrived, and do not commit until the final verdict is `passed: true`.

For Phase 13–16 hardening, require executable evidence for operational claims: start the built service before release rehearsal, run backup and restore against disposable SQLite files with real rows, exercise load scripts against more than `/health`, and re-run the fresh fail-closed review after fixes. If a review identifies a dead-path helper (for example recovery with no producer/trigger), wire both the producer and automatic trigger before claiming acceptance. For cross-service rehearsals on Windows, use the package’s real launcher (`dist/main.js` when `dist/index.js` is the library entry) and let the supervisor start processes; keep the rehearsal script focused on driving the live HTTP/WS flow. Treat generated SQLite/temp artifacts as data: inspect them, add correct ignore rules, and require explicit consent before deletion.

### Phase 13–16 evidence traps found in fresh review

- **Optional security is not fail-closed security.** If a release/administrative credential is enforced only when `NODE_ENV=production` or only when an env var happens to exist, test the default deployment too. A bound authoritative ID does not compensate for an unauthenticated release endpoint.
- **A dashboard JSON endpoint is not operational alerting.** Require an actual delivery path (or an explicit production startup failure), a named producer/trigger, and a rehearsal that proves alert delivery. A sink that silently returns when unconfigured is missing acceptance.
- **Accessibility state must have a consumer.** Trace every setting into the renderer/effect/audio path. A class with no CSS rule, or state used only by its checkbox, is decorative and should fail the acceptance matrix.
- **Rehearsal claims must match assertions.** Do not accept `released: true` unless the script observes downstream release and available state. Do not call a load test meaningful when its repeated paths are only `/health`, `/ready`, and `/metrics`; require at least one authenticated lifecycle path under load.
- **Localization scans must include JSX literals.** Dictionary wiring is partial if visible labels, control options, notification text, or product names remain hardcoded. Scan rendered JSX after adding locale dictionaries.

A compact session-specific checklist is in `references/godforge-phase13-16-review.md`; keep new findings here only when they generalize across Phase 13–16.

Do not turn a partial UI toggle or a test-only event into acceptance. Trace the setting/event from the real producer through the runtime consumer, and distinguish implementation gates from PRD acceptance in the final verdict.

### Phase 13–16 closure additions

- **Allocation/release is a two-sided lifecycle, not an endpoint checklist.** Trace every allocation producer (ranked, custom room, retries) to every completion/remake/abort path. Require the API to retain the authoritative server/match binding for each allocation, invoke release on every terminal path, and require the game-server release request to be authenticated and bound to that allocation. A release endpoint plus one happy-path caller is not acceptance.
- **Recovery helpers need a producer and trigger.** For payment recovery, backup restore, or incident replay, prove the state can actually enter the recoverable state in production and that a worker/startup/manual trigger executes it. A helper querying `status='pending'` is dead code when all production writes go straight to `granted`.
- **Observability must be operational.** A `/metrics` response with a few counters is not a dashboard, alert, trace, or health system. Map each PRD metric/alert to a producer, exposure surface, and executable verification; include required correlation fields at service boundaries.
- **Runbook prose is not rehearsal evidence.** Run the documented backup/restore, kill-switch, incident, allocation/release, and compensation workflows against started services. A script that only checks `/health`, `/ready`, and `/metrics` cannot prove release operations.
- **UI toggles must affect the real path.** For localization/accessibility/audio, trace settings into all user-facing strings and expensive/rendered effects. A CSS class that suppresses transitions while the simulation/render loop continues is partial; a browser notification test event is not enough unless the real backend event reaches the client.
- **Phase 16 determinism must use the match contract.** Re-running `createWorld(seed)` or stepping two worlds proves only primitive simulation determinism. Acceptance requires the same seed, config, and recorded inputs through the competitive match path, with canonical state hashes at defined checkpoints.
- **A green rehearsal script is not proof of the feature it omits.** Read every path exercised by release/load/E2E scripts and compare it to the PRD flow. A script that probes only health/ready/metrics cannot prove load integrity, and a local UI test event cannot prove backend notification wiring. Add a smallest real seam probe for each lifecycle boundary.
- **Probe allocation binding with a deliberately different authoritative id.** Allocate a custom match id, then attempt release with the player-derived id; a 409 binding mismatch proves whether the API retained the authoritative match id. Require the API's real release path to use the returned id and verify server state returns to available.

6. **Client-trusted progression/economy endpoints = fake economy.** When a client can POST progress directly, verify server authority before calling acceptance met:
   - Self-awarded XP grant route (`{amount: 1e9}` → max level, all unlocks) with no cap/source check AND no other production caller of addXp — grep callers; the grant route may be the SOLE XP path with the source param ignored.
   - Client-supplied mission progress (`{progress: 999}` → instant completion; negative values decrement counters below goal).
   - Cadence reset (daily/weekly wipe) callable by ANY authenticated player → global griefing; also check whether reset is automatic on the cadence boundary or manual-only (manual = missions never reset in production unless someone calls the endpoint).
   - Client-supplied entity ids on creation endpoints (bot minted with a human's playerId → impersonation surface even when an `isBot` flag is structurally always true).
   - Rewards wired: PRD "XP from Mission/Achievement" means completion handlers must CALL the award — a trigger that only records, never rewards, is a missing acceptance.
   - Pass side to verify: achievement idempotency = Set-backed trigger (duplicate trigger → 1 entry).
7. **Commerce/economy phases need transactional proof, not happy-path tests.** For every wallet, purchase, redeem, pass, and payment rule:
   - Inspect the actual schema and migration path. Runtime DDL and JSON blobs for relational code eligibility/rewards are not normalized, migration-managed persistence.
   - Use two service instances against the same on-disk SQLite DB. Verify conditional purchase/redeem limits, SQL balance increments, ledger count, and provider transaction uniqueness. `BEGIN IMMEDIATE` + a unique key can serialize these; service-local Maps cannot.
   - Trace the whole grant transaction: uniqueness/limit record, wallet or inventory grant, ledger, receipt must commit together and roll back together. Test the route layer as well as the service.
   - Check every eligibility field in the PRD makes it from admin input → persisted schema → server-authoritative account/rank/season source → redemption check. A domain type field which the HTTP mapper drops is missing acceptance.
   - Treat region/time as server-side trust data on **both** currency purchase and provider callback; client/provider product IDs must not bypass product availability.
   - Verify free-track entitlement has an authenticated route, while premium entitlement cannot be freely granted. Verify persisted receipts are retrievable only by their owning authenticated player.
   - Cosmetic fairness requires more than a `competitive: false` label: trace grants/equipment into ranked simulation/stat calculation and confirm no gameplay-stat field exists.
8. **Return structured JSON**: `{passed, blockers, missing_acceptance, fixes, phase_scope_notes}`. Blockers = acceptance criteria met only via stub/fake + security holes. Fixes = minimal diffs (stdlib-first: node:crypto scrypt over bcrypt dep, session-token map over auth framework). The PARENT TASK may mandate the exact schema (e.g. `{passed, blockers:[{id,severity,finding,evidence[]}], acceptance_matrix:{criterion:{status,evidence}}, missing_acceptance, phase_scope_notes}`) — use the task's schema verbatim; blockers can carry severity ('blocking'/'minor'/'info') and a criterion reached only partially (API met, console display broken) is 'partial' with `passed:false`, not 'met'.

## Re-verification pass after blocker fixes (claim-by-claim)

When re-reviewing a tree where a prior review's blockers were supposedly fixed, treat every claimed fix as a hypothesis. For each blocker/missing-acceptance item from the prior review:

1. **Map the claim to code**: read the CURRENT file (fresh, not the diff you remember) and `git diff` vs HEAD — a fix that changed only tests, or only comments, didn't land.
2. **Map the claim to a regression test**: find the test that FAILS if the fix regresses (e.g. the "unsticks all 4 participants" domain test for a busy-leak fix). Fix with no failing-if-regressed test = weaker evidence; note it.
3. **Grep for removals**: claims like "removed hardcoded X / dead function Y" are verified by `grep -rn "X" apps packages --include="*.ts"` expecting ZERO refs in src (exclude dist/node_modules).
4. **Compare counts between review passes**: a suite count shift (e.g. 76 → 77) means tests were added/removed — enumerate per-file `it(` counts and reconcile. Same count with different files = replaced tests, check nothing was deleted instead of fixed.
5. **Re-run all gates yourself** (tests, build, typecheck, lint, format) — claimed-green is not evidence.
6. **Design-inherent trust risks are observations, not blockers**: when acceptance as stated is met but the design trusts the client (e.g. `participant_ids` is client-supplied, so an omitting client could strand a teammate busy; explicit `active` list can include already-eliminated ids), list under observations — but say explicitly why it's inherent to the accepted design, so the parent decides.
7. **Claimed behavior with no failing-if-regressed test → run the ACTUAL source yourself.** Fixes that changed behavior but added no test that fails on regression ("50 XP one-time on crossing goal", "ultimate withheld below 80 energy") are unverified claims. Execute the real code with boundary assertions instead of trusting the tests that happen to exist:
   - Pure-TS modules (no imports beyond types) run directly: copy source files to a temp dir, import them from a throwaway probe with `node --experimental-strip-types probe.mjs` (Node ≥22.6; no build, no tsconfig, no vitest).
   - Assert exact boundaries, not happy paths: ultimate at energy 79 (withheld) vs 80 (used); XP exactly 50 once and 0 on repeat; clamp at 1000; `'abc'` → NaN → 400; unknown mission id inert.
   - Avoid `tsc` for this: ad-hoc file lists silently pick up the repo root tsconfig (`noEmit` → exit 0, nothing emitted), and cross-drive `.bin` shim invocation mangles spaces in paths (see windows-admin-bash).
   - **If the package has a built `dist/`, verify HTTP behavior through the real server.** `require('apps/api/dist/server.js')` from a throwaway `.cjs` in %TEMP% and drive routes with fastify's `app.inject()` — no tree edits, no tsx/vitest needed. This empirically catches route-shape issues tests miss: field truncation (full-payload round-trip diff), status-code choices (500 vs 404 on unknown resource), and missing runtime validation (invalid enum accepted → 200). Delete the probe after.
8. **Security/declarative-only fixes are only real at the route layer.** If the original blocker was a control that existed on paper (ranked replay lock, spectator hiding, admin gate), verify the fix is enforced by the HTTP route AND that the regression test drives the route via `app.inject` — a service-level unit test alone would have passed before the fix too. Service-fixed-but-route-open is the same bug in a new costume.
9. **Progression must have server-owned producers and cadence.** If player-facing XP/mission routes accept amount/progress, they are a cheat surface even with per-request clamps. Prefer 403 authority rejection and wire rewards from an authoritative match/result/tutorial/achievement producer; assert valid/invalid match behavior and idempotent triggers. Daily/weekly reset needs a server-owned startup check plus an unref'd cadence timer (or a real scheduler), not only an admin endpoint. Bot creation must reject caller-selected human IDs; use a reserved namespace or generated opaque bot ID, and keep ranked bot integration explicit if deferred.

## Security-hardening diff review (result-authoritative / lifecycle / binding)

When reviewing a diff that claims to close trust-boundary bugs, verify each fix at root cause and — critically — distinguish what the diff INTRODUCED from what pre-existed. Use `git show HEAD:<file>` on the touched paths to decide pre-existing vs regression; a pre-existing gap is an observation, a diff-introduced one is a blocker.

- **Server-authoritative result — verify the winner is unforgeable, not just "derived server-side".** The fix is real only if the authoritative value (`match.winnerCivilizationId`) is set by server simulation alone and no WS/intent path can set it. Trace every message type into the simulation (surrender/use_power/ready) and confirm none writes the winner field. The result route must ignore client `winner_id`/`loser_id`/`valid`, derive winner from the server outcome, and hard-require `status==='finished'`. The authoritative result endpoint must itself be token-gated and fail closed when the token is unconfigured (503 outside test), so clients can't read/abuse it. Removing a previously client-trusted `valid` flag is a win, not a loss.
- **Lifecycle guard coverage — check placement, not existence.** A `!allocated || lifecycle !== 'running'` guard only works if it sits at the TOP of the WS/entry handler BEFORE type dispatch. Verify it guards reconnect/use_power/ping/surrender too, not just the first/ready path. Guard after rate-limit + message parse is fine only if parsing is side-effect-free.
- **Authorization binding completeness — a ready/join seam gate is not a session binding.** If `authorizedPlayers` is checked only on `player_ready`, an unbound socket can still issue sibling intents (`use_power`, `surrender`, `ping`) as a joined authorized player's id, and the game loop validates NO session token on those paths → impersonation of an authorized player. This is the "auth ≠ authorization / per-entity ownership" trap at the connection layer. Confirm the binding, not the join step: reject intents whose playerId isn't the bound connection for that socket, or require the session token on all non-idempotent intents.
- **Claim-taken-before-await must be restored on EVERY new validation return, not just the original branches.** A hardening diff that adds new 409/400 checks AFTER a synchronous claim (`running → settling`) can wedge the entity: the diff restores the claim on the success and the original failure paths, but its OWN new validation returns (e.g. `MATCH_NOT_FINISHED`, `OUTCOME_MISMATCH`) bail out WITHOUT `restoreSettlement`. Result: the match is stuck `settling` forever (`beginSettlement` requires `running`), players stay busy, allocation leaks. Walk EVERY return path added by the diff and confirm the pre-await claim is rolled back on each — this is the "failure paths restore pre-op state" rule, but the diff's own new branches are the ones that slip.

## Provider-specific commerce verification (Stripe pattern)

When a commerce phase names a provider but runtime secrets are intentionally deferred, implement and test the provider boundary without secrets rather than leaving a generic boolean stub:

- Search the repo, `D:\` project/document paths, and prior session history for the provider name and existing contract before asking the user to resend requirements. Treat the PRD/API/DATABASE/ADR docs as the source of truth if they already contain the contract.
- For Stripe webhooks, preserve the exact raw JSON body before parsing; verify `Stripe-Signature` HMAC with `STRIPE_WEBHOOK_SECRET`, enforce a timestamp tolerance, accept only intended event types/statuses, derive the canonical player/product from signed provider metadata, and use the provider event/payment ID as the idempotency key.
- Fail closed when `STRIPE_WEBHOOK_SECRET` or the SKU→Stripe Price ID map is missing. A verified signature alone is insufficient: require the product's expected Stripe Price ID (and validate amount/currency when the provider catalog is available).
- Keep test/admin callback adapters separate from the production webhook route. Add a regression test for invalid signature and valid signed raw payload; restore process environment variables in `finally`.
- Report “provider runtime setup deferred” separately from “provider verification unimplemented.” Never ask for secrets; ask only for a missing provider identity/contract, then research public provider docs.

## Fresh-review execution discipline

- **Isolate the live rehearsal.** Before starting services, verify the requested ports are free and record the exact process/environment. A stale service on the same port can make a rehearsal hit the wrong build/config and produce misleading failures. Prefer fresh API/game-server ports for the final pass; verify `/health` and the game-server `/metrics` before driving flows.
- **Probe success is not whole-script success.** Alert probes that intentionally induce an outage may pass their targeted assertion while the surrounding health check correctly fails. Report the probe result separately and do not treat the expected nonzero wrapper exit as a feature failure.
- **Transient Vitest probes must live under the repo root.** Vitest's include/root discovery may ignore an absolute temporary test outside the repository. For a fresh seam probe, place the smallest test under the relevant package, run it, then remove it and verify `git status --short` shows no probe artifact. For fail-closed allocation/release, assert the exact sequence: downstream failure → HTTP 503 and retained binding; retry uses the authoritative downstream match ID and succeeds; a subsequent release reports the resource is no longer started. This catches swallowed release errors and accidental state clearing, not just a happy-path 200.
- **Run real seams, not only health endpoints.** Final Phase 13–16 evidence should include a fresh authenticated queue → allocation → result → release flow, load traffic beyond `/health`, kill-switch/payment rehearsal where configured, and an alert probe with the named predicate. If a script's URL/defaults or required environment differs from the started service, correct the invocation or classify the evidence as invalid rather than passing it.
- **Backup/restore evidence must inspect integrity and required tables; populate rows when the acceptance concerns durable data.** A schema-only restore with zero rows proves only file readability. Use disposable files/paths outside the repo for generated probes and leave the reviewed tree untouched.
- **UI acceptance needs runtime wiring checks.** Build success and state variables are insufficient: confirm settings are consumed by the rendered/effect path, and trace backend/WebSocket events to the browser notification path. Distinguish a local test-event button from the production event seam.

## Fresh commerce recovery checks

For payment flows with a pending/recovery path, do not stop at grant idempotency. Probe the full post-recovery read path: enqueue/verify → recover → wallet/inventory → authenticated receipt retrieval. Assert the receipt payload itself transitions from `pending` to `granted` and contains the final reward; updating only a status column while leaving serialized receipt JSON stale is an acceptance failure. Add this as a route-level regression when the receipt endpoint exists.

For GM-console acceptance, separate API capability from console demonstrability. A backend route/test is not enough for a criterion explicitly assigned to the web console: compare every rendered field to the actual response keys, and verify that requested mutations (ticket/bug/report/moderation/feature actions) are reachable from the UI rather than merely exposed by HTTP. Classify API-met/UI-missing as partial, not passed.

## Pitfalls

- **Tool-output redaction masks as `***` — the file is usually FINE.** When grep/read/python-repr shows `***` where `Bearer <token>` should be, it's display-layer masking, not corruption. It also hits non-secret tokens (`string | undefined` → `string *** undefined`) and python `repr()` output. Don't conclude files are corrupt or tests broken: `grep -c` counts pass through unmasked (fast sanity), and a raw-bytes hex dump is immune — `python -c "d=open('f','rb').read(); print(d[i:i+70].hex(' '))"` (or `sed -n 'Np' f | od -c`).
- Phase code may be uncommitted working-tree changes — `git log --oneline` shows nothing; check `git status --short`.
- **Multi-phase PRD docs: a bare grep hits the roadmap, not the spec.** A master doc listing ALL phases (roadmap overview) matches "Phase 10" long before the actual `# PHASE 10 — ...` spec section (Godforge: overview ~line 1417, spec ~line 2316). Locate with `grep -n '^# PHASE'` and read the section under that heading, not the first grep hit.
- **Phase 10 replay/spectator false positives.** A reducer wrapper that returns all stored events, a ranked flag supplied by the client, or a streamer `view()` helper with no production caller is decorative rather than acceptance. Trace non-test producers and consumers through the route; distinguish in-memory persistence and join-policy contracts from deferred durable storage/live transport. See `references/godforge-phase10-review.md`.
- Tests only count as coverage if they would FAIL when the acceptance breaks. Regex/shape assertions ("field matches ws://") prove nothing about real allocation/behavior.
- Auth/persistence/allocation gaps usually CANNOT be covered by tests in the current design — that's exactly why they are blockers, not just missing tests.
- **Commit state after fallible external calls.** If startRoom sets match_id BEFORE the allocate call, a 503 bricks the room — every retry returns ALREADY_STARTED with no server. Mark-as-started only after the downstream call succeeds, or revert on failure. Correct shape = validate → call downstream → confirmStart(roomId, actor, ticket) as the commit step; a 503 then leaves the entity retryable.
- **Docs drift is a real finding category, not a blocker.** Repo rules often mandate "update API.md when contract changes" — check docs/API.md, DATABASE.md, .env.example against the actual routes/fields. Mismatch (paths, auth scheme, new env vars missing from .env.example/ENVIRONMENT.md, version-string drift) → report under `missing_acceptance`, not `blockers`, unless the phase's own acceptance criteria name docs.
- **Fastify request-logging noise in vitest output.** Logged requests interleave with results; get clean counts with `grep -E "Test Files|Tests [0-9]+"` (or run that package's suite alone). Comparing claimed vs actual per-file `it(` counts via grep is the cheapest count check. Piping the suite output straight into grep can come back EMPTY (stream buffering/escape) — capture first (`pnpm --filter @godforge/api test > /tmp/out 2>&1`), then `grep -oE "src/[a-zA-Z-]+\.test\.ts \([0-9]+ tests?\)" /tmp/out`, sum per-file counts to reconcile claimed deltas (e.g. "91 = 89 + 2 new route tests" → verify which files gained what).
- **Committed vs working-tree file detection.** `git log --oneline -1 HEAD -- <file>` exits 0 even when the file does NOT exist at HEAD (silently misleading). `git ls-tree HEAD --name-only <dir>` is authoritative for "is this file committed" — pair with `git status --short` to separate modified from untracked (whole phases can ride along uncommitted in the same working tree).
- **Route allowed-value sets must equal the domain type's real values — a phantom value that passes validation but grants nothing is a silent no-op, not a bug report.** Commerce class: an admin compensation route accepted `essence`/`gold` while `Currency = 'coins' | 'shards'` and `grant()` only wrote coins/shards — a "successful" 201 that credited nothing. Verify by asserting the wallet/inventory/ledger actually changed for EVERY accepted currency, AND that values outside the domain type are rejected (check both directions).
- **Root dev scripts must be tested as commands, not inferred from package metadata.** On pnpm workspaces, a path selector such as `--filter './apps/*'` may match zero projects in the target environment. Prefer explicit package selectors for the apps that actually expose `dev` scripts (for example `--filter @godforge/api --filter @godforge/game-server --filter @godforge/web-game`), then run the root command and verify each child emits its ready/start signal.
- **Manual UI acceptance needs a real browser pass after gates.** Start API, game-server, and web app as separate supervised processes; navigate Home → Lobby → Play → Settings; click a real power and inspect the rendered target state; verify settings controls and browser console errors; probe API/game-server health and metrics. Do not claim browser acceptance from a build or synthetic event alone.
- **Live visual evidence must exercise the real producer path.** If a renderer state depends on an authoritative event (for example settlement destruction), source inspection, a unit test, or a screenshot of an ordinary world is insufficient: trigger the event through the actual player flow, capture the resulting state, and check console errors. Do not add a debug-only power, query flag, or fake state solely to manufacture evidence; classify the evidence gap and expose the feature through the real loadout/flow when that is the intended product behavior.
- **Native controls need stable browser semantics.** A control can look correct in an accessibility snapshot yet remain unverifiable if its DOM role/label is unstable or the driver cannot address its option. Give runtime-critical controls stable accessible names/IDs and verify the actual state transition (for example locale `en-US → th-TH`) after interaction. A failed browser action is not proof the feature is broken, but it is also not proof that the feature passed; inspect live DOM/state and report the evidence gap fail-closed.
- **Windows supervised dev processes can outlive the wrapper.** After stopping a parallel pnpm watcher, inspect ports with `netstat -ano`; terminate only the known Godforge listener PIDs with `taskkill.exe /PID <pid> /T /F` before rerunning a port-bound rehearsal, otherwise `EADDRINUSE` can make the test hit stale code.
- **Delegated review died before returning its verdict (HTTP 429 / max_iterations)? Recover findings from the live transcript.** The subagent's `think` lines and last tool results usually contain the blockers with file:line evidence even when the final JSON summary never generated. Grep `C:/Users/Acer/AppData/Local/hermes/cache/delegation/live/<delegation_id>/task-0.log` for `think` entries and the final read/grep results. Fix what you find, re-run gates, re-dispatch — never claim a pass from a dead review, and never trust the previous attempt's (unreceived) verdict.
- Binary-flagged docs: `read_file` may report a UTF-8 md as "binary" even when the file is entirely clean (no null bytes at all) — `file` says UTF-8 text; read via `sed -n 'X,Yp' doc.md` alone usually suffices, pipe through `tr -d '\000'` only if `od -c` actually shows nulls.
